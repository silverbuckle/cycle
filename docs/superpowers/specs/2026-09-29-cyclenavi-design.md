# CycleNavi プロダクト仕様案

更新日: 2026-09-29。状態: ユーザー承認済み（「進めてください」）。合意したプロダクトの方向性をまとめる。実装・提供開始を意味しない。技術選定と各実装単位は実装計画で具体化する。

## 1. 合意済みの目的

多少遠回りしても、自転車で楽しく快適に走れる道を選ぶ。遠回り許容度を指定し、自転車を目視できる飲食店や駐輪設備の情報を使って休憩できる。利用・投稿・共有が情報資産として蓄積するサービスを目指す。

- ロード・クロス・グラベルに対応。日常移動、週末ライド、宿泊を伴うバイクパッキングを扱う。
- iPhone先行。地図画面と音声によるナビを中心とし、画面消灯中も案内する。将来のAndroid版とサーバーを共有する。
- 全国・世界で使う設計とし、最初の実走品質検証は東京西部・神奈川で行う。世界でのデータ品質や提供可否を一律に保証するものではない。
- BIKEPACKING.comをトーンと旅の紹介方法の参考にし、YAMAPをエコシステムの参考にする。
- 出先の修理に対応するサイクルショップを探せるようにする（実装計画作成中の追加要望）。

## 2. 体験と画面構成の提案

主な入口は「マップ」「旅を探す」「記録」「マイページ」。マップから日常移動をすぐ開始でき、旅を探す画面には日帰りと宿泊コースを載せる。

基本フロー: 自転車プロフィール → 目的地または時間・日数 → ルート比較 → 休憩・宿泊を含む計画 → 地図・音声案内 → 記録 → 任意の公開・現地情報の提供。

自転車プロフィールは車種・タイヤ幅・電動アシスト。今回の条件として未舗装路の許容、坂、交通量、景色、遠回り上限を指定する。車種だけで路面の好みを固定しない。

日常移動では到着時刻、週末では時間内の周回、宿泊旅では日別の負荷と宿泊地点を優先する。

## 3. 道選びと案内

- 通行可能な最短所要時間の候補を基準に、追加時間または割合で遠回り上限を指定する。時間は推定値として表示する。
- 通行規制と路面の除外条件を先に適用し、その範囲で交通ストレス、登り、景観、投稿情報を評価する。評価の根拠と不明区間を表示する。
- 「最短」「快適」「景色・寄り道」の比較候補を提示する。制約内に候補がなければ理由と緩和案を示し、勝手に制約を変更しない。
- 案内画面は現在地、進行方向、次の曲がり角と距離、到着予想、次の立ち寄りを表示。音声は事前・直前案内とルート逸脱通知。
- 再探索は好み、立ち寄り、当日の宿泊先を引き継ぐ。残りの許容時間に収まらない場合は明示し、宿泊先を自動で置き換えない。
- GPS精度低下時は位置の不確かさを表示し、誤った曲がり角案内を抑制する。
- 宿泊旅では出発前に地図・行程・案内・スポットを保存する。圏外での保存ルートの表示と案内を要件とする。圏外での新規経路探索は別の技術検証項目とし、利用できない場合は明示する。

## 4. 休憩・駐輪・宿泊

スポットはカフェ、飲食店、駐輪場、給水、トイレ、修理、宿泊、キャンプ場を分類する。各属性には情報源、確認日、写真、確認状態を持たせる。

- 飲食店: 自転車が見える席の位置、テラス、ラック、地球ロックの可否。
- 駐輪場: 固定物、有人管理、入退場管理、営業時間。設備情報を示し、盗難の安全保証としない。
- 宿泊: 室内持ち込み、施錠保管、屋根、洗濯、充電、食事、チェックイン時間。未確認は未確認と表示。
- キャンプ場: 利用可能な施設と条件を確認して掲載。任意の空き地を宿泊可能地点として提案しない。

### 修理対応サイクルショップ

販売店と修理受付を区別する。ショップ詳細にはパンク・チューブ交換、チューブレス、タイヤ、ブレーキ、変速、ホイール等の対応項目、対応車種、他店購入車の受付、持ち込み・予約の条件、住所・電話・営業時間・修理受付終了時刻を持たせる。項目は「対応」「非対応」「未確認」を区別する。部品在庫、当日の待ち時間、当日修理完了は確認できた場合のみ確認時刻とともに表示する。

マップとナビの停止中メニューに「修理できる店を探す」を設ける。修理内容と車種で絞り、まず対応条件、次に到達距離で候補を示す。「営業時間内と推定」と「修理受付確認済み」を区別し、電話・公式ページで確認してから経由地へ追加できるようにする。店舗発信と利用者の実績報告は別の情報源として表示する。

走行できない場合は押し歩きで到達できる候補を探す。押し歩き経路が取得できない場合は経路未確認と表示し、自転車用経路を押し歩き用として流用しない。到達できる候補がない場合も明示する。店までの移動は独立した寄り道として扱い、予定の宿泊先と旅程を保持したまま到着時刻への影響を再計算する。通常営業情報だけから「今すぐ修理可能」と判定しない。

宿泊コースは日別の距離・獲得標高・路面・推定走行時間・休憩・補給・宿泊を持つ。荷物ありのペースを考慮し、チェックインに間に合わない計画を通知する。初期版の予約は施設の公式ページ等へのリンクとし、空室・予約完了をアプリが保証しない。

最初は編集・確認した宿泊コースを掲載し、宿泊先や日程を変更できる形にする。任意地域での複数日コースの完全自動生成は後続の検証とする。

## 5. 表現の方向性

BIKEPACKING.comの写真、旅のストーリー、実用的なコース情報の組み合わせを参考にする。以下は本アプリ独自のデザイン提案であり、参考サイトの色や書体を実測した結果ではない。

- 探索画面: 風景を主役にした大きな写真、短い旅の紹介、日数・路面・登り・補給を読み取りやすく配置。
- 色: 生成り、チャコール、深いグリーンを基調に、案内に必要な強調色を使う。
- ナビ画面: 屋外で読めるコントラストと文字サイズ、少ない操作を優先。
- 舗装路で巡る宿泊旅も掲載し、ロードやクロスの利用者も自分に合う旅を見つけられる表現にする。
- 写真・文章・コースデータは自作、許諾または適切なライセンスの素材を利用する。

## 6. YAMAPから学ぶ循環の提案

「探す → 計画 → ナビで走る → 記録 → 現地情報を共有 → 次の人の計画が良くなる」を中心にする。以下はYAMAPの実装の説明ではなく、本サービスへの適用案。

活動記録は軌跡と写真から下書きを作り、本人が公開範囲を選ぶ。記録と再利用可能な推奨コースを区別し、実走軌跡をそのまま通行可能な推奨ルートとして扱わない。

現地メモは点だけでなく道路区間・進行方向・観測日時に紐づける。路面、走りやすさ、通行止め、補給、駐輪・保管の情報を短い選択式入力で集める。投稿は停止中または走行後に促す。

「行ってみたい」は発見・共有の評価、「現地で確認した」は情報の信頼性の評価として分ける。再確認、役に立った実績、訂正への対応を貢献表示に反映する。投稿数や速さによる競争を主軸にしない。

期限や再確認の必要性は情報の種類ごとに扱い、古い情報・相反する報告を表示する。通行止めの解除は経過時間だけで判断しない。通報、重複統合、修正履歴、運営確認を用意する。

共有ページには写真、ルート概要、休憩・宿泊、作成者、保存導線を載せ、未登録でも概要を閲覧できる。公開軌跡は自宅周辺を隠し、写真の位置情報や文章からの漏れにも対応する。公開日記から現在の宿泊先を自動公開しない。

モートの仮説は、車種・路面・時間帯・方向に応じた区間情報と、現地で再確認されたスポット情報、その履歴。人数だけでなく情報密度・鮮度・訂正速度を育てる。

## 7. 事業と段階的な展開の提案

初期はナビ、スポット、旅の記録と共有を接続する。初期データは実走確認と掲載許諾のある投稿から整備し、投稿の少ない地域でも基礎地図で利用できる範囲を明示する。

次の段階で地域のコース作成者、店舗、宿泊施設が情報を更新できる機能を検討する。店舗自身の申告と利用者の確認を区別する。

収益は高度な旅程計画・保存管理等のサブスクリプション、宿泊等への送客、自治体・地域とのコース企画を候補とする。価格と無料範囲は利用検証後に決める。広告・協賛は表示し、走りやすさの評価に混ぜない。物販・保険・独自ポイント通貨は初期実装に含めない。

## 8. 構成と開発の分割

iPhoneアプリは地図表示・位置取得・音声・ローカル保存を担当。サーバーはプロフィール、経路条件、スポット、コース、投稿、共有と確認履歴を担当する。基礎地図と経路エンジンは交換可能な境界を設ける。

主なデータ: BikeProfile、RouteRequest、Route、RouteSegment、Trip、DayStage、Stop、Place、Observation、Activity、Verification。Tripは複数のDayStageを持ち、宿泊Stopは前日と翌日をつなぐ。Observationは点または区間と確認根拠を持つ。

実装仕様は以下の単位に分ける。本文はプロダクト全体の仕様であり、各単位のAPIやSDK選定を確定する実装計画ではない。

1. 地図・音声ナビと快適ルート比較。位置情報権限、消灯中の案内、再探索、保存ルートの動作を実機検証。
2. 休憩・駐輪・宿泊・修理対応サイクルショップと、日別行程を持つ旅の探索・計画。1泊2日の旅と、途中の故障でショップに立ち寄る行程を通しで検証。
3. 記録・共有・現地メモ・再確認と運営機能。公開範囲と情報更新の循環を検証。

地図・経路提供元は、日本の自転車通行情報、世界の対応範囲、オフライン利用、利用条件、費用を比較して実装計画で決定する。表示上の世界対応と、検証済み地域を区別する。内部は単位・言語・タイムゾーンを表示形式と分離する。

## 9. 検証と成功の判断

- 同一出発地・目的地で、許容した追加時間内に本人が快適だと感じるルートが得られるか実走比較する。
- ロード・クロス・グラベルで路面条件を確認し、除外条件が破られないことを確認する。
- 画面消灯、音声割り込み、GPS低精度、逸脱、圏外、アプリ再起動を検証する。電池消費を実機測定する。
- 複数日旅で宿泊地点が再探索で失われず、日別の距離・時間が整合することを確認する。
- 修理店では受付条件不明、他店購入車非対応、受付終了、車体を押す必要がある場合を検証し、対応できない店を修理可能と案内しない。
- 地図と共有ページで非公開情報が露出しないこと、古い情報・矛盾した報告・通報が扱えることを検証する。
- 利用の指標はナビ完走率、ルート満足度、再利用率、スポット情報の再確認率、共有コースの保存から実走への転換。数値目標は初回実走の基準値を得て設定する。
